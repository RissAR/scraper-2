# ТЕХНІЧНЕ ЗАВДАННЯ: Фінальний аудит безпеки, усунення помилок та підготовка до деплою на Ubuntu Server

## 1. Мета та огляд
Провести фінальний інженерний аудит кодової бази `RieltorBot`, виявити та усунути всі приховані вразливості, гарантувати безперебійну роботу бази даних при конкурентних навантаженнях та перевірити готовність до деплою в Docker-контейнері на Ubuntu Server.

---

## 2. Чек-лист та обов'язкові завдання аудиту

### БЛОК 1. Аудит безпеки (Security Hardening)
1. **Вилучення чутливих секретів із кодової бази:**
   * **Проблема:** У `config.py` параметр `BOT_TOKEN` містить захардкоджений токен як дефолтне значення.
   * **Виправлення:** Прибрати дефолтний токен: `BOT_TOKEN: str = ""` (значення повинно підтягуватися виключно із `.env`).
   * Перевірити `.env.example`, щоб там були присутні тільки безпечні приклади без діючих токенів.
2. **Захист від збоїв парсингу Telegram через спецсимволи (`TelegramBadRequest`):**
   * **Проблема:** Назви, описи та райони з OLX або DIM.RIA можуть містити символи `<`, `>`, `&` (наприклад: `<VIP>`, `1к & студія`), що ламає HTML-парсер Telegram.
   * **Виправлення:** Провести ревізію `format_listing_message`, `format_dict_listing_message` та всіх статусних повідомлень. Гарантувати, що **всі динамічні поля ззовні** проходять через `html.escape()`.
3. **Строга перевірка прав у Callback Handlers (RBAC Enforcement):**
   * **Проблема:** Неавторизований користувач може надіслати підроблений `callback_data` (наприклад `toggle_olx`, `proxy_delete`, `export_excel`) і виконати адмінську дію в обхід інтерфейсу.
   * **Виправлення:** У кожному чутливому обробнику інлайн-кнопок гарантувати перевірку:
     ```python
     if not settings.is_admin(callback.from_user.id):
         await callback.answer("⛔️ Ця дія доступна лише адміністраторам!", show_alert=True)
         return
     ```
4. **Маскування паролів проксі:**
   * Перевірити логування та виведення проксі у `proxy_checker.py`, `keyboards.py`, `bot.py` — паролі проксі (`user:password`) повинні обов'язково маскуватися функцією `mask_proxy()`.

---

### БЛОК 2. Аудит стабільності та конкурентності (Concurrency & DB Reliability)
1. **Захист від блокування SQLite (`database is locked`):**
   * **Проблема:** Одночасні асинхронні транзакції від двох скраперів (OLX + DIM.RIA) та користувачів у Telegram можуть спричинити блокування файлу бази даних.
   * **Виправлення:** У методі `init_db()` в `database.py` обов'язково увімкнути режим WAL та таймаут зайнятості:
     ```python
     await db.execute("PRAGMA journal_mode = WAL;")
     await db.execute("PRAGMA busy_timeout = 5000;")
     ```
2. **Коректне завершення процесів (Graceful Shutdown):**
   * При отриманні сигналів `SIGINT` / `SIGTERM` (при перезапуску або зупинці контейнера `docker compose down`):
     - Безпечно зупинити фонові задачі сканування.
     - Закрити всі активні сесії Playwright та `httpx.AsyncClient`.
     - Завершити пул з'єднань із базою даних без пошкодження SQLite файлу.

---

### БЛОК 3. Аудит Dockerfile та docker-compose.yml для Ubuntu Server
1. **Перевірка `Dockerfile`:**
   * Встановлення Playwright та системних бібліотек:
     `RUN pip install --no-cache-dir -r requirements.txt && playwright install chromium --with-deps`
   * Наявність та права директорії `/app/data`.
   * Встановлення коректної часової зони `TZ=Europe/Kyiv`.
2. **Перевірка `docker-compose.yml`:**
   * Монтування томів `./data:/app/data` (збереження БД `rieltor_bot.db` та логів `bot.log` між оновленнями контейнера).
   * Політика авто-перезапуску `restart: unless-stopped`.
   * Налаштування ротації логів контейнера (`max-size: "10m"`, `max-file: "3"`).
